# Reliability release (2026-10-06)

## Operator behavior
- Local printing: pause/cancel before in-app navigation. Back/route teardown cancels future sends. A batch already handed to Dazzle/WebUSB may still print; this is not a hardware emergency stop.
- Progress uses a durable browser outbox. Pending sync/storage problems remain visible. Do not clear browser storage with pending updates. A new local batch waits only for that run's pending progress to sync; other runs are not blocked.
- Network errors, 401 (sign in again), 408, 429 and 5xx keep retrying in order per run. Permanent refusals (400, 403, 404, 409, 410, 422, e.g. the run was deleted elsewhere) are set aside with a plain-language reason and Export/Discard buttons; they never block printing.
- Run progress is a high-water mark for progress-only updates: the server keeps the highest `printedCount` it has seen, so a late or stale progress update cannot move the resume position back. On this build, an update that also carries a status is held to the same rule; only "Go back to label N" rewinds it, with an explicit `resetProgress` that applies only if progress hasn't moved since the person tapped it (compare-and-set). On main (`50ea233`), and from any tab that has no `X-LW-Client` header, an update that carries a status is an exact write (see Rollback procedure).
- "Go back to label N" writes its "Went back to label N" history entry on the server, in the same statement as the guarded progress change, stamped with the database's time, so the cutoff it sets can't land late. The client sends a key with the go-back (`X-LW-Rewind-Key`); the response says whether the entry was written (`X-LW-Rewind-Event: written` or `none`), and the client then never sends the entry itself. A server without those headers (main) gets the old separate entry, exactly as before. A lone "Went back" entry that no guarded go-back wrote is refused (409 `rewind_not_applied`); main's tabs never send one. A key is applied at most once: the guarded update also requires that no history entry with that key exists yet, so a retry of a go-back whose answer was lost (after another device printed on) can't move progress back a second time. That retry is answered 409 with `alreadyApplied: true` and the written headers; the page then shows "Went back to label N" in the history, reads the run, and if another device printed past it says so in one line and offers "Resume from label X" (never a reprint). A go-back whose answer was lost is retried once after a second, then by the outbox as before; "Send now" is the only button name used for it.
- The Runs list polls lightly: every 5–15 s it reads the print history and office summary only for runs that are queued, printing or paused, changed in the last 10 minutes, or have office work moving; all runs are read again once a minute and when the tab comes back. The history comes back as merged stretches worked out in the database, not one row per scan. Indexes that would make these reads cheaper (`run_print_events(run_id, event_type)`, `office_requests(run_id)`, `office_jobs(request_id)`) are a schema change and are not part of this build.
- Deleting a run with print history, a preset used by runs, or a format used by designs is refused with a 409 and an explanation; the item is kept. Templates are archived rather than deleted.
- Runs retain an immutable template/format snapshot. Template edits affect new runs, not reprints of existing runs. Pre-release runs are marked as captured from the design available during this update; this cannot reconstruct original artwork that was already overwritten.
- Template saves require their loaded revision. Conflicts leave the local draft intact; recover/save as a separate template instead of silently replacing someone else's edits. Failed saves stay in the tab, and recoverable drafts are offered when reopening a template. Recovery copies do not overwrite the saved design.
- Old tabs without revision support receive a refresh-required error. Duplicate unsaved work before refreshing; do not discard unsaved edits.
- Libraries load metadata in bounded pages. Artwork is loaded on opening a template; full native-run output is prepared only for an explicit print/export range. Initial counts/search results fill as the remaining metadata pages arrive.
- API errors retain last-good lists; failed deletions do not remove records locally. Retry/session-expiry controls are visible.

## Verification and release
- `npm test`: deterministic offline regressions; no database/printer access. Included in `npm run build`, so failed checks block deployment.
- `npm run typecheck`: compile-time validation.
- `node scripts/production/verify-browser.mjs http://localhost:3150`: synthetic browser check. ALL API and Dazzle requests intercepted; never prints physical labels.
- `node scripts/production/verify-database.cjs`: opt-in real database integration in a uniquely named isolated schema, synthetic rows only. Verifies snapshots, atomic save conflicts, validation and stale-progress rejection. Test schema retained for inspection.
- `node scripts/production/measure-loads.cjs`: read-only list payload comparison (not an end-to-end timing claim).
- Vercel build gates on regressions and its own TypeScript compilation. GitHub Actions is staged at `docs/pending/github-checks.yml`: current OAuth authorization lacks workflow scope, so it cannot yet be installed at `.github/workflows/checks.yml`. After activation and a passing run, require the `checks` status on main. Do not claim GitHub CI/branch protection is enabled until then.

## Migration / rollback
- Run `node scripts/production/backup-verify.cjs /absolute/private/backup/directory` before migration. Backups are confidential, mode 0600, outside the repository. This script reads six application-data tables under a consistent snapshot, then rehearses exact restore into transaction-local temporary tables. It does not back up office credentials, printer-pairing state, or the entire provider instance.
- `node scripts/production/migrate.cjs` adds nullable `runs.design_snapshot` and captures CURRENT designs for unsnapshotted existing runs. Idempotent; no progress/template updates and no removed columns. Run before deploying code that reads that column.
- Rollback can restore the previous application deployment without removing the additive column. Older code does not enforce snapshots/revision checks, so rollback weakens those guarantees. Do not drop the snapshot column.

## Rollback procedure
1. In Vercel, promote the previous production deployment `dpl_B3jJhkAhYdCn3urt7PCDHBFFVm3K` (main, `50ea233`, which added the optional blank label at the end of an Office Pi send). Not `dpl_8jXofwmB9VdFPqYaRiQPsH4XaMPv` (`ffda577`): that one predates the blank-label option. No database step: this branch has no schema change or migration, and the Pi API and printed bytes are the same, so office stations keep polling and printing.
2. Right away, reload every open Label Wrangler tab (shop tablets, office computers, phones) so each runs main's page code. Do not clear browser storage on any device. Until a tab is reloaded it runs this build's page code against main's server (see below).
3. Tell the people printing that, on main, a busy run's progress can move back (next section), and to check the run's progress before they resume.
4. Print-only accounts: this build lets a `print-or-edit` account save progress (`PUT /api/runs/[id]` with progress fields) and print history; main refuses both with 403. Before the rollback, have print-only people let their devices finish sending (no "saved on this device" notice left on their open runs), or give those accounts edit access until the rollback is done. Otherwise their queued progress and history updates (`lw:run-op:`) are refused by main, and main's outbox, which has no per-error handling, can keep retrying them ahead of newer updates on that device. If that happens, give the account edit access so main accepts them, then take it away again once the device shows nothing waiting.

What happens to work still queued on a device:
- Ordinary progress and print events saved offline stay in main's outbox keys (`lw:run-op:`), so main's code sends them after the reload. On main only progress-only updates are a high-water mark. An update that carries a status (for example `{printedCount: 40, status: 'printing'}` from a laptop that was offline) is an exact write on main: if it lands after another device reached 60, progress drops to 40. Main behaves this way today; this build doesn't make it worse, but it can happen during a rollback while devices catch up.
- A "Go back to label N" still waiting on a device is stored apart (`lw:run-op-v2:`), with its print-history entry. Main's code never reads or sends it, so it cannot stall main's outbox or hold up new batches. If you need that go-back on main, do it again there (Reprint from). If the deployment is later rolled forward, that device sends it then; it is applied only if the run's progress hasn't moved since, otherwise it is set aside with a plain "wasn't applied" notice.
- A tab of this build that was not reloaded sends a go-back as a guarded rewind. Main refuses it ("Invalid field resetProgress"), and this build never resends it as an unguarded exact write, because that could erase progress made in between. It is set aside with a plain notice ("“Go back to label N” wasn’t applied: Label Wrangler just updated. Reload the page, then go back again if you still need to. Nothing was changed."). When the go-back was pressed on that page, the page instead shows one "This page is out of date" block with a Reload page button, and hides the go-back button until the reload. Its print-history entry is never sent. Updates set aside earlier stay in Export/Discard.
- Office sends waiting for an answer (`lw:office-pending:<run>`) carry over unchanged: same key, same payload (including `endBlank` when a blank label at the end was asked for), same idempotency key, so a retry from main can't print twice and keeps or leaves out the blank exactly as first sent. A "Send all in parts" plan (`lw:office-parts:<run>`, which remembers that only the last part ends with the blank) is this build's only; main doesn't read it, so after a rollback main doesn't offer the remaining parts. Send them from main's form, ticking "Blank label after this run" only for the send that ends the range. This build also keeps `lw:office-held-blank:<run>` (which held send should end with the blank after a "Print in order" fix); main doesn't read it, so after a rollback tick main's box yourself for that send. In this build the box starts off for every send and goes back to off after each one. A printer control (pause/resume) is different: this build saves a new one per account (`lw:office-control-pending:<user>`), which main can't read. Only a control first saved by main on that device (the device-wide `lw:office-control-pending`) is copied across, and that device-wide copy stays until the same control is answered. So after a rollback, main neither shows nor resends a pause or resume that was made on this build and never answered. The office printer's own state is what counts: before the rollback, check the printer bar on the Runs list and press Pause or Resume again on main if it isn't in the state you want.
- This build also keeps `lw:office-pending-prior:<run>` (the office requests for the same labels that already existed when a send was saved, so the queue can tell the saved send's own request from an earlier one; main never reads it) and `lw:office-blank-due:<run>` (a blank label a "too big" split couldn't carry, due on the send that ends the range; main doesn't read it, so after a rollback tick main's box yourself for that send).
- Reloading or closing a tab while its send is on its way leaves the shared "sending" mark (`lw:office-sending:<run>`, 12 s) and records no failure. The reloaded page says "Checking whether the office got labels…" with Send off, looks the key up after 1, 2, 4, 8 and 15 s, and settles as soon as the office has it: same key, still one job. On main (no key lookup) the page settles from the office queue instead: when the queue lists a request for the saved labels made after the save, it says the labels are on their way; when it lists one that may be older, it says they look like they arrived and offers "They arrived, clear this" first (Send again, same key, beside it). On this build, a key lookup that answers "not there" (and no tab holds the sending mark) settles at once: "The office didn’t get labels A–B", with "Send labels A–B" (same key, so it can't print twice). While this tab's own mark is live the page looks every 2 s, so a send that lands mid-check settles at once. A tab that finds another tab's live mark shows "Sending … from another tab" and makes no lookups; renewals of the same mark (every 4 s) are not news. A tab's id is kept only on a reload, and a page that finds a live page with the same id (Chrome's Duplicate tab copies it) takes a new one, so a duplicate never treats the original's send as its own. There is no "Start over": "They arrived, clear this" is offered when the queue lists the labels, and "Forget this send" (which throws the saved key away) asks first, saying that sending them again later can print them twice.
- After a rollback, a tab of this build that was not reloaded can show a bigger printed count on the run page than the Runs list. That is expected, not lost progress: main's Runs list counts only the run's progress (`printedCount`, it sends no `countedSpans`), while the run page also counts office ranges a person confirmed and labels printed by scanning, read from the print history. Reloading the tab (step 2) puts both on main's count. Making the run page show main's count without a reload would need it to read the history differently while the server is on main, so it is left as is (it heals on reload). Without those counted stretches this build's Runs list names no "Still to go" range, so the two pages never list two different ranges.
- A go-back sent from a tab of this build to main carries `X-LW-Rewind-Key`, which main ignores; main refuses the guarded rewind itself, so nothing is written and no entry is sent (above). Rolled forward again, a go-back that was already applied and answered before the rollback is never sent twice: its entry has the go-back's key as its id.
- Print history keeps any "Went back to label N" entries (event type `rewind`). Main has no words for that type, so it lists them as "Went back to label N labels A–B"; it otherwise ignores them. The cancel entries this build records (what was stopped at the office, what was never sent) are ordinary `cancelled` events, which main lists as plain history lines.

## Office panel and run page (round 14)
- "Stop after this part and leave" (from a link while "Send all in parts" runs) stops the check of a part that hasn't gone yet, removes the page's own "Leave site?" warning, then leaves through the app's router: one question, not two. The panel says "Leaving after part N…". No part is sent after the one already going.
- The office panel has one status line, chosen by urgency (a send that needs the person, then a refusal, then sending, then queued), then the office queue as a plain list. A queued notice is not shown when the status line already says it.
- Before "Send the last part" / "Send the remaining parts" is offered, the office queue is read once more; pressing it reads the queue again and sends only parts the office doesn't have (one request per part, each with its own saved key).
- "Pause printer" stays on while the office printer is stopped for a check, so a manager can hold everything after the check too.
- A barcode that won't scan still waits for its "Print anyway" tick (a send the exact renderer refuses never goes, and one it can produce never stops), and the reason is said right above the Send or Start button. Text the printer can't print doesn't hold the button on a native (ZPL) design; it is named beside it, saying what prints instead ("30 labels will print a box where “·” should be"), and a finished run says what printed instead.
- The run page reads the run again when its tab comes back into view (at most every 10 s, never while it prints or while this device has unsaved progress for the run), so a count another device moved shows before a go-back from an old number.
- A run saved as "printing" reads "Printing" only while something is: a print on that page, office labels on their way, or progress in the last 5 minutes. Otherwise it reads Ready.
- Print history says "then one blank label" for a send this device asked a blank for (the browser keeps which requests had one). Another device can't tell: the office request doesn't store the blank in a field the app reads, and adding one would be a schema change, so that is left for the owner.

## Office panel and run page (round 15)
- Labels already printed anywhere count before a send: progress, office ranges a person confirmed and labels printed by scanning. The suggested range stays inside the first gap. A typed range that crosses printed labels asks first, names them, and offers only the true gaps ("Send 41–60, 81–99 and 102–120", one part per gap) or one gap; printing them again is its own choice. Checked in this build and against main's server (no `countedSpans`: the page reads the print history itself).
- "Send all in parts" checks every label of the series for ones the exact renderer refuses (a cheap pass, no drawing) before the first part goes, and names only those labels. It offers to send around them; "Leave label N out" on the run page does the same for any office send. A single spreadsheet row reads as data ("Label 2,600’s SKU is too long for this label (44 characters)"). "Send the last part" never does nothing: it sends, offers to send around a bad label, or says why nothing was sent.
- The time of each send is kept with its key. Until the server's limit for that send (about 310 s) has passed, a lookup that finds nothing says "The office hasn’t got labels A–B yet", with the same-key send; after it, "The office didn’t get labels A–B", and the lookups stop. A send saved without its time (by main or an older page) counts from when the page started looking.
- "Forget this send" re-reads the saved send under the same Web Lock a send takes, against the key the person saw when they pressed it: a send another tab is making, or a new one it saved, is never forgotten. Saving a new send clears the old refusal record.
- On a picture (bitmap) design, a character the bundled fonts can't draw stops the labels that have it, with the label, field and character named, before the tap (the renderer refuses them). The glyph table mirrors the bundled Liberation fonts with the renderer's own rule; `test-run-b15.cjs` checks it against the font files.
- Only a thermal run can wait for the office printer on the Runs list; a sheet run never reads "Waiting".
- Four status dots by meaning (ready, working, needs you, done or stopped) on the list and the header, and one colour rule for every progress bar (printed solid, labels at the office not counted yet in a lighter tint). The header says "Checking" while labels are checked. A server message the app doesn't know reads "Something went wrong on our side", with the raw text behind "Details".
- After "Use a QR code instead", the new run offers to cancel the old barcode run (one tap and a confirm; a run with labels waiting at the office is left to its own page), and the old run's page says a QR run replaced it. This link is kept on the device that made the QR run.
- "Mark sent labels as printed" on the Runs list reads the office queue and the print history again before it writes, and writes only when the plan is the one the person saw.
- The rollback count difference above (run page vs Runs list after a rollback to main) is unchanged: it heals on reload.

## Office panel and run page (round 16)
- A saved "Send all in parts" plan is trimmed by every label counted as printed (progress, office ranges a person confirmed, labels printed by scanning), the same count a fresh send uses. "Send the last part" after labels 1501–1600 were scanned sends 1601–2000. A part split by a printed island goes as two parts. Printing them again stays its own choice.
- "Send all in parts" takes the same per-run Web Lock as a single send and keeps a short-lived series mark (`lw:office-series:<run>`, 12 s, renewed every 4 s). Another tab on the run says "Sending part N of M (labels A–B) from another tab…" and offers nothing that sends until the series ends. A running series never takes another tab's range. If the office refuses a part because it already has those labels, the panel says so ("…sent from another tab or device. Nothing was sent twice.").
- When the label an end blank was to follow is left out (it can't print), the blank moves to the new last send and the dialog or the box says which label it now follows. With every label in the boxes left out, the button reads "Nothing to send".
- The cancel offer after "Use a QR code instead" now needs the explicit link the new-run page saves (`lw:qr-replaces:<new run id>` = the old run's id). There is no clock guess any more. It shows only while the old run exists and isn't printing, finished or cancelled, and the old run is read again before the cancel. The old run's "replaced by" line shows only while that link exists.
- USB: a typed range that is all printed already ("3–4" after 1–8) is "Print 3–4 again". It prints them a second time and leaves progress alone. "Start at N instead" starts right away.
- The bad-character stop says "Needs you · Label N can't print" in the header. It says its sentence once, names the file row beside the label ("Label 5 (row 6 in your file)"), and moves the preview to that label. The check also covers a barcode's human-readable line, drawn in Liberation Sans Regular as the renderer draws it.
- After a rollback, when the older server refuses a go-back, the page says "Going back to an earlier label can't be done right now. Nothing was changed." It remembers this on the device (`lw:go-back-refused`) and stops offering the go-back, even after a reload. A range that crosses printed labels resumes at the next label instead. On a later visit, one read of `/api/version` (no data, no database) turns it back on once the server has that route.
- A run whose office part holds the shared printer for a check is never "Done" or a green "All printed". It reads "Needs a check" (red) and sits with the unfinished runs showing "Waiting for a check". Red is only for needs you. Sent reads as working. A run held behind another run reads "Waiting" with a calm dot, and "Paused" is kept for a paused printer. The list says what the bar's lighter part is ("25 sent, not counted yet"). Printed labels that don't run in one stretch from label 1 read "65 of 120 printed", with a line listing them ("Printed: 1–40, 66–90"). The sent line says "and one blank label" when the send carried one.

## Permissions notes
- A print-only account can change a run's progress fields through `PUT /api/runs/[id]` (`print-or-edit`): `printedCount`, `status` and `completedAt`. That includes completing or cancelling a run, which is intended: an operator finishes or cancels the run they print. Everything else on a run (name, data, design) needs an edit account.

## Browser hardening
- `next.config.ts` sends nosniff, Referrer-Policy, X-Frame-Options DENY, a Permissions-Policy that keeps WebUSB (`usb=(self)`), and a report-only CSP on every path except `/api/print-stations/*` (Pi responses are unchanged). The CSP is not enforced because the app uses WASM, a pdf.js worker, inline scripts in the sheet print tab and the Dazzle localhost bridge.
- The pdf.js worker in `public/` is copied from the installed `pdfjs-dist` by `scripts/copy-pdf-worker.cjs` (run by `npm run dev`/`npm run build`); `npm test` fails if they differ. Keep pdf.js on v4.

## Monitoring / operational boundaries
- Client JavaScript failures and >500ms main-thread tasks emit bounded, authenticated structured Vercel logs (at most 10 reports per document). No label values, package tags, query strings or stack traces are transmitted by this instrumentation.
- Hosting alert routing, provider point-in-time recovery retention and scheduled off-machine backup policy are not established by this code change. The verified private backup/restore rehearsal is not a replacement for those operator settings. They require provider-level configuration/access and remain explicit operational follow-ups.
- Physical printer behavior is not certified by mocked tests. Delivery acceptance is not physical-label confirmation.
